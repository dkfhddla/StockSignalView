# ADR 0001: 초기 로컬 웹 아키텍처 채택

## 상태

Accepted

## 맥락

StockSignalView는 개인 투자자의 거래 기록, 투자 메모, 시장 대비 상대성과 분석을 한 흐름으로 연결하는 투자 운영 시스템이다. 초기 단계에서는 빠르게 검증 가능한 로컬 실행 구조가 필요하다.

제품 구상에는 뉴스, 공시, AI 동적 대시보드, 실시간 시세, 증권사 연동이 포함되어 있지만, 첫 단계에서 모든 외부 연동을 동시에 구현하면 보안과 운영 복잡도가 커진다.

## 결정

초기 아키텍처는 다음 기준을 따른다.

- 프론트엔드는 React와 Vite를 사용한다.
- 백엔드는 Python FastAPI를 사용한다.
- 데이터베이스는 SQLite로 시작한다.
- ORM과 마이그레이션은 SQLAlchemy와 Alembic 사용을 전제로 한다.
- 초기 실행 환경은 Local PC 또는 NAS를 우선한다.
- 증권사 주문 기능은 기본적으로 비활성화한다.
- 후속 외부 투자처 연동은 읽기 전용 시장 데이터와 주문 실행 경계를 분리한다. `ReadOnlyMarketDataProvider`는 보유 종목, 현재가, KOSPI/KOSDAQ 지수를 읽기 전용으로 조회하고, `BrokerOrderAdapter`는 주문 또는 dry-run 주문만 담당한다.
- 주문 관련 기본값은 `dry_run=true`로 둔다.
- AI 동적 대시보드는 AI가 코드를 직접 생성해 실행하지 않고, 자연어를 Dashboard Schema JSON으로 변환한 뒤 검증된 렌더러가 표시한다.

## 결과

이 결정으로 MVP는 종목 관리, 거래 기록, 포트폴리오 계산, 상대수익률 계산, Dashboard Schema v1, 기본 위젯 레지스트리, 동적 렌더러, 기본 알림에 집중할 수 있다.

뉴스, 공시, 고도화된 AI 분석 요약, 외부 AI API 실제 연동, 실시간 시세, 외부 투자처 연동은 아키텍처의 확장 지점으로 남긴다. 읽기 전용 시장 데이터는 `ReadOnlyMarketDataProvider` 경계에서 먼저 검증하고, 주문 기능은 별도의 `BrokerOrderAdapter`와 보안 기본값·로그 정책이 구현된 뒤 연결한다.

## 대안

### 처음부터 Docker와 PostgreSQL로 시작

운영 환경에 가까운 장점이 있지만 초기 개인 사용 검증에는 설정 비용이 크다. SQLite에서 시작하고 PostgreSQL 전환 가능성을 남기는 편이 현재 단계에 맞다.

### 프론트엔드 없이 백엔드 API만 먼저 구현

계산 로직 검증에는 유리하지만, 사용자가 거래 기록과 대시보드를 실제 흐름으로 확인하기 어렵다. 제품 방향상 프론트엔드와 백엔드 경계를 함께 유지하는 편이 적절하다.

### AI가 직접 화면 코드를 생성

자유도는 높지만 보안과 검증 문제가 크다. Dashboard Schema JSON과 제한된 렌더러를 사용하는 방식이 안전하다.
